# Worklog — 2026-09

## 2026-09-26 — E42: public-history features — the MEMORY question, answered NULL on the current net (and E6's negative was never a test of it)

Branch `feat/e42-public-history`. Plan: `docs/e42-public-history-plan.md`
(pre-registered 2026-09-25, before any run).

### Why this exists

The user asked whether E6's LSTM negative (-0.105, 2026-07-03) could have been
our own architecture mistake. Re-read of `feat/rppo-lstm` (rppo.py, driver,
verdict): **no code bug, but three design choices made the result uninformative
about memory itself.** (1) `BattleEnv` resolves the opponent's whole turn inside
`step`, so the agent never observes an opponent action — cards that leave no
board trace (items, removal, burn, a traded creature) are invisible at every
timestep, and no recurrent state over own-decision observations can carry "what
the opponent revealed". (2) The zoo and the avg-hard3 ruler are greedy
hand-dumpers: hand contents are a near-deterministic function of
`(turn, op_hand_count)`, both already observed. (3) 800k steps from scratch on
the old transformer trunk with batch 64 -> 2048 at the same lr and step count
(~32x fewer updates). So E42 asked the cheapest form of the question: make the
PUBLIC history explicit (opponent's played cards, their turn-end mana/hand log,
own remaining deck as an order-destroyed multiset) and train under a regime whose
opponents DO hold cards. Those features are a superset of anything an LSTM over
own-decision observations could accumulate, so a null here also closes the LSTM
retest.

### Plumbing (kept; default paths byte-identical)

`PlayerState.played` / `PlayerState.turn_log` (engine bookkeeping, replay format
untouched); `BattleView` gains deck counts, `my_deck_cards` (SORTED — fairness
test: shuffling the live deck changes nothing), `op_played`, `op_turn_log`; token
variant **`fxh`** = fx + a 25-wide `hist` obs key (`encode.hist_features`);
`SlimTokenExtractor` grows a zero-init `hist_mlp` branch only when the key
exists — **SB3's `ortho_init` runs after the extractor's own init and silently
un-zeroed it; `training._rezero_hist_branch` fixes that** (without it the
warm-start identity would have been false). `locma/envs/warmstart.py` rebuilds a
model at the old hyperparameters across obs spaces and copies weights
(step-0 identity tested vs `depot:e36` gen7); `nohist` trailing param on
`ppo:`/`lppo:` zeroes hist at play time; driver `--obs-mode/--warm-widen/
--pool-from`; ladder `--extra-net`. Scripts: `e42_gate0.py`, `e42_gate1.py`,
`e42_guard.py`, `e42_branch_diag.py`.

Mechanism (`scripts/e42_branch_diag.py`, 1774 decisions from 40 H-vs-C games):
the trained branch is alive but small — 0.115 of the scalar branch's magnitude,

### VERDICT: NULL for the memory hypothesis (pre-registered row 2). Not promoted.

P1 is positive but P3 keeps most of it and P3b is exact parity: the small edge
does not depend on the history information. Under the plan's table that is
"gain is branch capacity / optimizer restart / chain variance, not information —
null for the hypothesis". Single-seed, 2M warm steps; the +0.027 is inside the
band E36's own chains swing between generations. What Gate 0 promised (a few
points of R2 on the opponent's hand composition, nothing on realized damage) is
what the net did with it: nearly nothing.

Consequences, per the plan: **memory over public history is not a reactive-net
lever at this regime, and the LSTM retest (memo steps 2-4) is dead** — its
information set is a strict subset of what E42 handed the net explicitly. E6's
negative stands as a result, but its mechanism read is corrected: not
"memory is useless", rather "there was never anything to remember that pays,
and E6 could not have seen it anyway". The remaining reactive-net gap to depth
is still the opponent-reply ply (E39) — E39-align is the open arm.

Keep: the engine logs and `fxh` plumbing (cheap, fair, tested; reusable for a
token-level history variant if the item/tempo card design ever changes), the
widening warm start (general tool for obs-space escalations), `nohist`.
